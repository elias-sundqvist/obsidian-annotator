# Closing every open issue with the next release

**This plan supersedes [ISSUE_TRIAGE.md](ISSUE_TRIAGE.md)** (2026-11-11), which is kept as it was. It re-judges the same issues against the branch as of 2026-11-12, after areas on scanned pages, drawing, PDF export, taking in a PDF's own annotations, selection across page breaks, whole-book find, contents and type controls, damaged-note recovery, idle and start-up work, and annotation links that reuse an open pane had landed.

Source: `gh issue list --repo elias-sundqvist/obsidian-annotator --state open` on 2026-11-12. **271 open issues**, the same 271 numbers as the earlier triage: none opened, none closed, and none updated since 2026-11-10. Nothing was posted to GitHub.

Everything below describes the native reader, which was released as 0.3.0 on 2026-11-13. The text was written before the release, so where it says "the branch" or "the release" it means 0.3.0. What was then done with the issues is in "After the release" at the end.

### Page notes that know their page or chapter

Closes #57, #163, #182. Board: `issues-page-notes-page` under `pdf`.

- What it takes: A page note written while a PDF page or a book chapter is in view keeps that place (an extra field in the annotation JSON, which the original plugin preserves and ignores; or an optional page selector). The card shows "Page 12" and clicking it goes there; the sidebar can group page notes by page. Notes without a place stay as they are.
- Done looks like: New page notes carry the page or chapter; clicking one goes there; old page notes unchanged; the original plugin still reads the note (interoperability test); a test pins it.

### Every common way of writing annotation-target works, and the guide shows them

Closes #93, #386, #202. Board: `issues-target-forms` under `quality`.

- What it takes: Accept an embed `![[A.pdf]]` (preferences.ts annotationTarget strips `[[ ]]` but not the leading `!`), treat a non-breaking space in a file name like the space it looks like when resolving, and add a short section to GUIDE.md with the accepted forms: plain path, `[[wikilink]]`, `![[embed]]`, Markdown link, URL, and the Dataview inline field `annotation-target:: …`.
- Done looks like: Unit tests for `![[…]]` and for a target with U+00A0; GUIDE.md has a "Pointing a note at its source" section with a Dataview example.

### A template for copied and dragged annotation links

Closes #91, #280. Board: `issues-link-template` under `storage`.

- What it takes: One setting, "Copied link", that takes the export placeholders (`{{quote}}`, `{{link}}`, `{{location}}`, `{{note}}`, `{{date}}`, and `{{title}}`/`{{author}}` once PDF metadata exists) and is used by the card's link button, the drag, and "Copy link to selected annotation". Default stays the current form.
- Done looks like: Setting in place; drag, copy and the command all use it; a test fills the template; default output byte-identical to today.

### Where new annotations are written in their note

Closes #124, #167. Board: `issues-note-heading` under `storage`.

- What it takes: A setting for the heading a new annotation note starts with (default "# Annotations") and an optional template note for new annotation notes, so properties and a heading such as "## Highlights" are in place before the first block; new blocks keep being appended at the end. Writing into the middle of a note (after a chosen heading) is a change to the proved create operation and is left out unless the owner wants it.
- Done looks like: New notes are made from the setting or template; blocks append after it; existing notes untouched; a test pins it.

### Several default target folders, tried in order

Closes #150, #168. Board: `issues-default-paths` under `storage`.

- What it takes: "Default target path" accepts one folder per line, inside or outside the vault, tried in order; the first that resolves wins. Lets one synced setting work on Windows, macOS and Linux with different library folders. Outside-vault folders keep going through the existing confirmation and copy (LOCAL_FILE_TARGETS.md).
- Done looks like: Setting takes several lines; resolution order tested (in-vault first, then each folder); outside folders still ask first.

### Setting: open the annotation sidebar with a source, or not

Closes #125. Board: `issues-sidebar-on-open` under `quality`.

- What it takes: A toggle "Open the sidebar when a source opens" (main.ts openNoteTarget calls openSidebar unconditionally today). The command "Show or hide the annotations sidebar" remains for opening it later.
- Done looks like: Toggle present, default on; off keeps the sidebar closed on open and on following a link; test.

### A CSS class on annotation notes

Closes #308. Board: `issues-note-css-class` under `quality`.

- What it takes: Add a class (e.g. `annotator-note`) to Markdown views of notes that have an `annotation-target`, in Reading view and Live Preview, and document it in STYLING.md, so snippets can style the note's quotes without fragile selectors.
- Done looks like: Class present in both modes, removed when the property goes; STYLING.md lists it.

### An HTML file in the vault as a source

Closes #262. Board: `issues-html-in-vault` under `quality`.

- What it takes: Let `annotation-target` name an `.html` file in the vault (wikilink or path): open it through the same path as a saved reading copy (reading-copy.ts), so it is annotated offline and syncs. No `file://` URLs.
- Done looks like: An in-vault .html target opens and takes highlights on desktop and Android; test on a fixture page.

### Reading progress in a note property

Closes #285. Board: `issues-progress-property` under `storage`.

- What it takes: Optionally write `annotation-progress` (page/pages for PDFs, percent for books, time for video) to the annotation note when the source is closed or left, not on every page turn, so Dataview can list it. Off by default, because it rewrites the note.
- Done looks like: Setting off by default; when on, the property is written once on leaving; no writes while reading; test.

### Full-screen reading on phones

Closes #236. Board: `issues-phone-fullscreen` under `mobile`.

- What it takes: A command and a button in the reader's menu that hide Obsidian's header and navigation bars while a source is read on a phone (a class on the workspace, undone by the same button or Back).
- Done looks like: Works in portrait and landscape on Android; leaves no state behind when the tab closes; iOS checked in ios-pass.

### PDF title, authors and year into the note's properties

Closes #18. Board: `issues-pdf-metadata` under `pdf`.

- What it takes: A command "Add the PDF's details to the note" that reads the document information and XMP through the host's PDF.js (title, author, subject, keywords, creation date, and a DOI if the metadata has one) and writes the ones the note does not yet have as properties. No network lookup.
- Done looks like: Command fills properties without overwriting; test on a fixture PDF with and without metadata; the `{{title}}`/`{{author}}` placeholders become available to exports and the link template.

### Clickable tags in the raw note (only if the original reads it unchanged)

Closes #388. Board: `issues-tags-live-preview` under `storage`.

- What it takes: The tags line of a stored block is written exactly as the original plugin wrote it, so its `#tags` are not clickable in Live Preview. Writing a space after the `>` would fix it, but changes the block format: do it only if the published 0.2.11 parser reads the new line to the same tags (check with published-compatibility.test.mjs and the Bend block codec, with a law), and keep reading the old form.
- Done looks like: Either: new blocks write the clickable form, both readers agree (test and law), old blocks unchanged. Or: owner declines and the issue gets the reply in the table.

## Decisions for the owner

- ~~Release identity~~ **Decided 2026-11-12:** the release replaces the old Hypothesis/iframe plugin under the id `obsidian-annotator`, and the native code takes the place of the legacy code in the repository (board group `promote`). The "Closes with the release" replies hold: users of 0.2.11 get it as an update. The release notes should give before/after numbers for size, load time and idle cost (`promote-measure`).
- Editing the quote (#152, #310): keep the quote as the source has it (proposed: decline), or allow a displayed quote that differs from the anchored one?
- The note format (#24, #111, #256, #299, #388): confirm the format stays the original's. #388 needs a yes or no on writing `> #tag` if the original reads it unchanged.
- One file per annotation (`per-annotation-decision`): if adopted, it is the answer to #24 and #256 instead of a decline.
- Writing reading progress into notes (#285) and the full-screen phone mode (#236): both change things outside the reader's own view (the note, Obsidian's chrome). Do them, or decline?
- Writing annotations under a chosen heading (#124, #167): the proposed item only templates new notes; inserting in the middle of a note is a change to a proved operation.
- Whether to close "Closes after a check" issues that cannot be reproduced (no file, no device) with a reply asking to reopen, or to leave them open until a reporter confirms.
- Issue #415 (co-maintainer) and #209 (issue templates) are yours to answer.
- Pull requests #336 and #330: close them with the release, using the replies in "Forks and open pull requests". Board: `issues-open-prs`.
- annotator-plus (0shombh-d3v) is a maintained fork of the old reader, and the release replaces what it fixes. Do you want to tell its author about the release, or adopt its "highlights with a note" underline and filter after the release?
