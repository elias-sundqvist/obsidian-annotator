## Read back after host writes — 0.0.129

The installed desktop Obsidian1.14.5 runtime's app.js shows that its JSON writer catches adapter write rejections and resolves; Plugin.saveData delegates to that writer. Awaiting saveData alone therefore does not prove that recovery drafts, preferences or source associations reached the settings file. The inspected extracted source matches the installed obsidian-1.14.5.asar entry exactly, SHA25695b9fd3944625c3b88116878b03d655147fed8cdfe6ddf931f2064ead78ccd5b. No host source is shipped in the plugin. Its reader uses the same direct JSON parsing as the existing native malformed-settings guard; no separate byte-order-mark acceptance discrepancy was established.

Native persistence still serializes settings jobs and uses the host saveData API. Each job snapshots the expected serialized values, awaits the host, reads the settings file back, parses it and compares its reserialization. Whitespace changes are accepted. Missing/unreadable/truncated or differing data rejects the job with an explicit unverified-save error; current reader state remains available in memory and the queue permits a later retry. This is read-back verification, not an atomic disk transaction, distributed sync merge, settings-file repair or new Bend law. A damaged partial write is reported rather than treated as successful.

The test Plugin writer now performs the adapter write and models the observed host's swallowed adapter errors instead of only changing an in-memory object. The regression fails against the previous native implementation when a host save resolves without writing. Additional tests cover both plugin IDs, swallowed disk errors, truncation, replacement by unrelated valid JSON, retaining current preferences, retry success and harmless whitespace changes. All400 tests, release build and original-ID rehearsal artifact generation pass. Existing remote-revision rollback and draft persistence checks pass with the more realistic writer.

## Validated startup snapshot and host directories — 0.0.130

For an existing settings file, startup now adopts the exact snapshot it just read and validated instead of invoking a second host loadData read. A regression supplies a valid font-size/opaque-data snapshot while the host loader would return undefined; the old implementation calls that loader and loses the snapshot. Native now makes no second host call, adopts the correct preferences and retains the unknown field on save. A missing settings file retains the normal loadData first-install path. Native currently has no onExternalSettingsChange callback requiring host loadData modified-time tracking. This is a consistent startup snapshot, not distributed settings synchronization.

The file directory now follows the public PluginManifest.dir provided by the host, with the original configDir/plugins/id fallback when absent. Read validation and post-save verification use that same directory as the host writer. Original-ID upgrade checkpoint creation/validation also accepts this exact directory context. Existing standard-path version1 checkpoints are unchanged; custom-directory checkpoints still require exactly the three expected settings/workspace entries and reject a different directory context. No arbitrary backup paths become valid. This covers the plugin's own settings/checkpoint path, not a new automatic discovery feature for another legacy installation.

Both plugin IDs have directory/adoption/write regressions; a custom config/directory test verifies raw checkpoint retention, strict context and no overwrite after later preference changes. All403 tests, release build and original-ID rehearsal artifact generation pass. The test host writer follows manifest.dir as the actual host does.
